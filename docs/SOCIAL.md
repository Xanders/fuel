# Chat, names and analytics

## NameDictionary v1

The consumer supplies the dictionary. Fuel does not choose a game's naming policy or guarantee uniqueness.

```json
{"version":1,"fallback":"en","separator":" ","locales":{"en":[["Bright","Quiet"],["Fox","Owl"]],"fr":[["Petit"],["Renard"]]}}
```

Each locale contains ordered token pools. A full-name list is one pool; compositional names use multiple pools. Locale lookup uses normalized exact locale, then primary language, then the declared fallback. Selection is deterministic: for each zero-based pool index, SHA-256 of Crystal/JSON tuple `[1,seed,index]`, first eight hex digits interpreted unsigned, modulo pool size. Join selected tokens with separator (default one space). Persist chosen display names when dictionary changes must not rename existing players. Dictionaries and their licensing belong to the consumer. Names may collide; use account identity separately.

## Censor

`Censor.new(words, variants)` treats all dictionary words and glyph variants as literals. It matches case-insensitively at Unicode letter/number boundaries and tolerates punctuation between letters. Matched text is replaced by asterisks. It is a small filter, not comprehensive abuse detection: contextual abuse, every Unicode confusable and adversarial language require game policy/moderation. No automatic punishment is imposed.

Chat messages are plain text. Render as text, never raw HTML. Membership is checked on reads and writes. Guild membership is checked again on each request. Optional bounded PostgreSQL history is available for every channel kind. The supplied HTTP adapter limits message frequency per account and provides mutes and reports; see [API](API.md) and [storage bounds](ARCHITECTURE.md#resource-limits). Game-specific consent, block and moderation policy remain application responsibilities.

The default HTTP adapter delivers chat through bounded history polling. To disable history, construct `Chat` with `history_limit: 0` and a `delivery: ->(kind : String, target : String, event : JSON::Any) { ...; nil }` callback wired to the game's live transport. Without that callback zero retention is rejected with `delivery_required`. The callback receives the censored event after any configured history write and outside the chat mutex. It must check each recipient's current access and bound its own transport queues. For private messages the target is the recipient and the event's actor is the sender. No message is retained at zero history, so disconnected recipients cannot recover it. Delivery errors can mean an unknown outcome; do not automatically resend as a new player intent.

## Questmetry

Analytics is optional and inactive until configured. Keep the ingestion key server-side, configure namespace/environment/version and an event/property allowlist, and preferably supply a dedicated pseudonym key. Account/session identifiers use keyed pseudonyms. Reject free text, names, arbitrary URLs, credentials and raw account IDs in properties. The adapter does not create projects, dashboards or downstream retention policies.

Outgoing event IDs are limited to 80 characters; names must be snake_case and at most 80 characters, and environment is limited to 40. These receiver limits are checked before delivery-buffer admission. Client input IDs retain Fuel's 100-character key limit because the adapter sends their keyed 64-character form.

Validators are predicates over isolated copies: modifying their arguments cannot expand the queued payload or add unapproved fields. Standalone `capture` without an explicit revision first takes a short authenticated preference snapshot, stops immediately if disabled, and carries that revision through the later fresh admission check. Validation holds no account lock. Disposable server admission uses a nonwaiting row lock; a busy account can lose its analytical copy without blocking business work.

Delivery is best effort, with sender buffers only in RAM. `max_pending` defaults to 10,000 and bounds the combined deferred server admissions, accepted events and in-flight batch. One background admission worker checks server facts; it never waits in the business caller. `drain` sends at most 25 accepted events once, then discards that batch whether acknowledged with HTTP202 or rejected/unavailable. There is no retry, halt/recovery journal, disk/SQL payload write or restart replay. `pending` counts occupied slots; `omitted` counts capacity drops. Compatibility methods `halted` and `resume` return zero because no halted tail exists. Restart, overflow and unavailable delivery may lose analytics; gameplay must not depend on it.

`AccountTransaction#event` collects bounded analytical descriptors; Fuel offers them only after the business commit succeeds. An exact business receipt retry does not regenerate events. `Rules` hooks can use `SessionEvents#once`; facts use a separate RAM buffer (256 pending facts per room, 16,384 once IDs) and never consume persistent effect slots or create operation receipts. Removing a completed room hands remaining facts to a separate bounded registry buffer (256 facts total), leaving room-slot reuse immediate. Failed match candidates are dropped. Excess/invalid telemetry is dropped without rejecting a valid game mutation. Runtime offers at most25 facts per pass and runs one detached analytics pump; delivery does not count toward business `safe_to_replace` or shutdown completion.

For custom trusted producers, call `emit(account, id, name, session, properties, occurred_at, revision)` **after** successful business commit, carrying the trusted revision from fact creation. Unknown/negative revisions are dropped, never restamped after opt-in; framework actions/results freeze the revision at their authority boundary. It offers a bounded, nonblocking server admission. Authenticate the account through the business operation; this trusted API is not a public account-ID authority endpoint. Schema validation and a fresh preference check happen before acceptance into the delivery queue; failed/deferred admission may be dropped. `capture(credential,...)` remains an explicit synchronous authenticated admission for standalone analytics calls. Do not use it in a business transaction or make a product operation await it. The old transaction-bound `enqueue(connection,...)` API is removed; custom callers must move to post-commit `emit`. Closing Store stops further deferred admission without joining a blocked validator or sender.

UI events use `client_events` as an explicit subset of the event schema and the authenticated [HTTP endpoint](API.md). Unlisted outcome events are rejected. Raw client IDs are account-keyed in a separate server-owned domain, while context/source and receipt time remain server-owned. New admission validates the **current** stored enabled flag and optional preference revision. A client request created/sent before opt-out but first received afterwards is not accepted, even if its original event ID or occurrence predates that change. Revision mismatches remain stale after opt-in.

`Store#analytics_enabled` persists the account choice and increments its revision when changed, even with no delivery adapter. `Questmetry#enabled` delegates to it. Opt-out prevents new admission; it does not purge/scan RAM tail, filter it at delivery, wait for a blocked sender or cancel requests. Events already accepted into the delivery buffer may finish. Deferred server offers are not accepted tail until their fresh admission check succeeds. Removing an adapter neither resets the preference nor restores a queue. Progress, results, payments, audit and recipient retention are separate durable contracts.

### Upgrading an existing durable sender

Wire routes, preference revisions, SDK event calls and adapter configuration remain compatible. This is not a Crystal source drop-in for callers of the removed `enqueue(connection,...)` helper or for code expecting milestone `Effect` receipts/retry/halt behavior. Update those callers and verify the game's opt-out and deletion privacy text: a previously stricter promise about accepted tail must not silently weaken when changing pins. Neither opt-out nor account deletion cancels delivery of already accepted RAM tail, which can finish after acknowledgement; any stricter consumer/provider obligation needs an explicit adoption decision.

For a future authorized adoption, identify the exact namespace and all old writers/drainers; stop those old producers before switching to this sender. Take the project's normal consistent backup and record legacy row counts without exposing payloads. Existing migration/table definitions remain for compatibility; the new adapter does not read, send, clear, import or backfill those rows. Consent changes leave them untouched. Account deletion retains the ordinary SQL purge, tombstones and deletion-proof contract; it is independent of the accepted delivery tail described above.

Leave old rows inert until a separately authorized, namespace-scoped retention/cleanup decision. Never truncate a shared outbox or regenerate analytics from durable game receipts. An old binary rollback can resume sending old rows: keep its analytics disabled/stopped during rollback, preserve the stored preference, and explicitly review that delivery boundary before re-enabling. No existing consumer deployment, pin change or database cleanup is performed by upgrading this library's source.
